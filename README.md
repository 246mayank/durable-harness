# durable-harness

[![CI](https://github.com/246mayank/durable-harness/actions/workflows/ci.yml/badge.svg)](https://github.com/246mayank/durable-harness/actions/workflows/ci.yml)

**A Python agent runtime that resumes from a log instead of restarting, so side-effecting tool calls take effect once.**

Agents that act on the world fail halfway through: they create an ad, send an email, move budget, and then the process dies, a response gets lost after the server committed, or a retry fires. `durable-harness` journals every planner decision and every tool intent to a SQLite write-ahead log *before* acting. After a crash it **replays the log rather than re-asking the planner**. Each call whose outcome is unknown is recovered according to the tool's declared **effect class**: re-send it, re-send it under the same key, look it up, or escalate it to a human.

The guarantee is **at-least-once execution with idempotent effects**. A request may go out more than once, but its effect lands once. A call that can't be made safe is escalated, never guessed. The runtime is built and evaluated against a **simulated** ad/email platform with seeded fault injection. A B2B campaign agent drives it, using a scripted planner at scale and real LLMs on smaller samples.

## Why resume, not restart

Say a campaign agent crashes after creating the campaign and two ads. The obvious recovery is to run it again, but a planner asked again is a new draw. An LLM at temperature > 0 writes different ad copy, maybe in a different order. Every re-planned call carries new arguments, so even idempotency keys hashed from those arguments stop matching. The platform sees brand-new requests: duplicate ads, a second email blast to the same trial users, double spend.

Lost responses do the same damage with no crash at all. A request whose response is lost *after* the platform committed (a timeout, a 504 from a proxy) looks exactly like one that never arrived. Retrying a call with no idempotency support duplicates it; not retrying may drop it. Worse, a request can still be in flight after its timeout and land seconds later, so even looking it up and finding nothing doesn't prove it didn't happen. And a worker presumed dead can wake up and carry on.

So the runtime does three things:

1. **It never re-asks a decided step.** Decisions are journaled, and a restart replays them. The planner is consulted only for steps it has never decided.
2. **It keys by position, not by arguments.** A step's idempotency key is `hash(run_id, step)`. Replay pins step N to one decision, so a resumed step re-sends the same arguments under the same key.
3. **It recovers by effect class.** What is safe to do with an unknown outcome depends on the API, so each tool declares it.

And two more for calls that may still be in flight:

4. **Every send carries a deadline**, journaled before the send, after which the platform won't process it. A negative lookup is trusted only once the deadline has passed.
5. **Each incarnation fences off the ones before it.** A process that was presumed dead and wakes up can't journal or send again.

## How it works

### Write order and crash windows

Each step is written to the journal in this order, with every event its own committed SQLite transaction:

```
decision  ->  intent (before the call)  ->  attempt*  ->  result (after the call)
```

| crash happens | journal holds | on restart |
|---|---|---|
| before the decision is written | earlier steps only | ask the planner: nothing was decided or sent |
| after the decision (`after_decision`) | decision | replay the decision and make the call |
| after the intent, before the send (`after_intent`) | decision, intent | outcome unknown: recover by effect class |
| after the platform applied it, before the result was journaled (`after_send`) | decision, intent | the same, and this is the nasty one |
| after the result (`after_result`) | decision, ..., result | step done: ask the planner for the next one |

The crash-matrix test injects a crash at each of the four points, at each of the 9 steps, at temperature 0 and 0.7. A second variant crashes again in the same place during recovery. In every cell the harness finishes with no duplicate, missing or excess effect, in exactly 9 planner calls.

Hooks also fire at `before_send`, after the fence check and just before the request leaves. A crash there looks the same as one at `after_intent`, but it is the one place where a hung incarnation can still send something once it wakes (see fencing below).

### Parallel tool calls

A planner can decide several calls at once (`{"calls": [...]}`), as LLM APIs do. The rules:
- **Steps:** the decision is one journal event, and the fold turns it into one step per call. Each call keeps its own positional key.
- **Intents:** all the calls' intents are committed in one transaction, with one fsync, before the first call goes out.
- **Recovery:** after a crash, each call is recovered from its own intent by its effect class, exactly like a single call. The batch is never re-asked.
- **Stopping partway:** if a call escalates or suspends the run, the calls this incarnation journaled but never sent get their intents voided. They re-execute later instead of being recovered as in doubt.

A parallel crash matrix (4 points × 9 steps × 2 temperatures × `harness` and `harness_cas`) checks that a batch never duplicates and is never re-asked.

### Failure taxonomy

Failures are classified by what the caller knows, not by what the server did ([harness/errors.py](harness/errors.py)):

| class | triggers | meaning |
|---|---|---|
| `NotApplied` | connection refused, connect timeout, 429, 408 (past its deadline) | definitely not processed: always safe to retry |
| `Ambiguous` | 5xx, 504, read/write timeout, connection reset | may have taken effect |
| `Rejected` | any other 4xx | processed and refused: don't retry, tell the planner |

A 500 counts as ambiguous even though this simulator's 500s always happen before commit. A real service can commit and then fail: it crashes while serializing the response, a post-commit hook throws, or a proxy sits in between. Only the server knows, and it didn't say. That conservatism costs escalations, and the benchmark counts them.

### Effect classes

| effect | tool | when the outcome is unknown |
|---|---|---|
| read | `get_metrics` | re-send |
| idempotent | `create_campaign`, `create_ad` | re-send with the same `Idempotency-Key`; the platform replays its stored response |
| reconcilable | `send_email_batch` | look it up by `client_ref` (the key); send only if absent |
| unsafe | `allocate_budget` | escalate to a human; never guess |

The planner never sees an unknown outcome of a side-effecting call, because it would re-plan the call as a new step under a new key. If retries run out while the outcome is still unknown, the run suspends, and the next incarnation recovers the step from its intent.

A tool is a plain function with a Pydantic argument model:

```python
@tool(Effect.RECONCILABLE, SendEmailArgs)
def send_email_batch(client, args, ctx):
    return request(client, "POST", "/v1/email/batches",
                   json={**args.model_dump(), "client_ref": ctx.key}, headers=ctx.headers())

@send_email_batch.reconciler
def _find_email_batch(client, args, ctx):
    found = request(client, "GET", "/v1/email/batches", params={"client_ref": ctx.key})["items"]
    return found[0] if found else None
```

### Idempotency keys

There are three modes, so they can be compared:

- `none`: no key.
- `args`: `hash(run_id, tool, args)`.
- `positional`: `hash(run_id, step)`.

Argument keys hold only while a re-planned call reproduces its arguments, which is true at temperature 0 and false above it. Positional keys are stable for a step whatever its arguments. They are correct **only together with replay**, because the journal pins step N to one decision. Without replay, step N after a restart could be a different call, and its positional key would collide with the old one. The platform answers that with a 409, and the benchmark's 409 column checks that it never happens.

### Escalation, approvals and budget

- **Escalation.** `resolve(journal, run_id, applied=True, value=...)` records an operator's answer. `applied=False` voids the intent, so the step re-executes under the same key. In the benchmark the "operator" waits out the call's deadline, lets any request still in flight land, and then looks the call's trace id up in the platform's audit log. That models a person checking the dashboard, which takes real time.
- **Approval gate.** With approvals on, an unsafe call stops in `awaiting_approval` until `approve(journal, run_id, step, args_hash)` is called. The approval is bound to a hash of the arguments, so approving $500 can't authorize $5,000.
- **Budget reservation.** With a cap set, an unsafe call is refused if committed spend, plus spend whose outcome is still unknown, plus this call would exceed the cap.

### Conditional writes

The allocation API is unsafe because nothing identifies a lost allocation. A precondition makes it checkable. The harness reads the campaign's total before writing the intent, journals that total with the intent, and sends it as `expected_total`. After a lost response:

- **Total unchanged:** it wasn't applied, so re-send. The re-send can't double-apply, because its precondition would fail.
- **Total grew by the amount:** it was applied.
- **Anything else:** escalate.

`harness_cas` in the results is the same runtime with this variant of the tool. It is also immune to delayed delivery: a late original carries the old `expected_total` and fails its precondition.

### Deadlines: calls still in flight

A 504 doesn't mean the request is gone. It may be queued somewhere and processed seconds later. A lookup that runs first finds nothing, the harness re-sends, and the original lands as a second email batch. The simulator models this as **delayed delivery**: the client gets a 504 at once, and the platform processes the request after a random delay.

The fix is a deadline. Every send carries `X-Deadline`, and the deadline is journaled with the intent before the send goes out. The platform won't process a request past its deadline: one that arrives late gets a 408 (`NotApplied`), and a delayed one is dropped. Recovery then has a rule it can trust:

- A **positive** lookup is believed at once.
- A **negative** lookup is believed only after the step's latest deadline has passed, because from then on no send of the step can land. The runtime sleeps until then and looks again.
- A re-send after that gets a **fresh deadline**, journaled first, so recovery always knows the latest one.

Idempotent calls don't need to wait: a late original and its re-send share a key. The operator waits out the deadline before checking the audit log. In-process runs share a `VirtualClock` with the simulator, so the waiting costs no wall time and runs stay deterministic. The hard-kill runner uses the wall clock both processes share.

### Fencing: an incarnation that comes back

A crash detector can't tell a dead process from a hung one. If the harness starts a replacement and the old process wakes up, both act on the same run: the old one, working from a stale view of the journal, would plan and send the rest of the workflow again.

Each incarnation therefore takes the run over with a new **epoch** (`Journal.acquire`). Every journal append carries the incarnation's epoch and fails with `Fenced` inside the same transaction if a newer one exists. Every send checks the epoch first. A woken incarnation's next write or send fails, and it stops with status `fenced`.

One gap is left: an incarnation that passed the fence check and hangs before its request leaves (`before_send`) still sends when it wakes. The deadline closes it. That request carries the deadline journaled for it, and the new owner waited that deadline out before acting on a negative lookup or an operator's check. So by the time the stray request arrives, the platform refuses it. The zombie experiment above switches each defense off in turn; it takes both.

### Journal durability

The journal runs in SQLite's WAL mode. Only the writes that a send depends on have to reach the disk before the send: its intent, and a renewed deadline. So by default (`send`) the journal fsyncs exactly those.

This is safe for two reasons. An fsync covers every frame written before it, and recovery after a power loss keeps a prefix of the log. Every call that went out therefore still has its intent and its latest deadline on disk. A power loss can only take the tail after the last send:
- a decision: nothing was sent, so the planner is asked again;
- an attempt record;
- a result: the step is recovered from its intent, as after any crash, at worst with one more escalation.

`full` (`synchronous=FULL`) fsyncs every write. `normal` never fsyncs. It survives a process kill, because committed frames sit in the OS page cache, but a power loss can take an intent whose call did go out, which is exactly what the journal exists to prevent.

Durability changes no decision the runtime makes, only what a power loss can take, so every count in the tables above is the same at any level. The tests check which writes fsync and exercise process death, not a real power cut. What each level costs:

## Honest limits

- **The simulator is part of this repo.** The results measure the runtime's correctness under the failure model it injects. They say nothing about campaign performance or about how any real platform behaves.
- **Deadlines need the platform's cooperation.** The deadline rule works because this simulated platform refuses to process a request past its deadline. Most real APIs make no such promise. Without it, the fallback is a timing assumption: wait longer than any request could stay in flight. The simulator checks the deadline when processing starts, which here is also the commit; a real platform would have to check at commit. Both sides read one machine's clock; across machines the margin would have to cover clock skew.
- **Fencing is journal-side.** It holds because both incarnations reach the same SQLite file, and the one stray send it can't stop is covered by the deadline. A distributed journal would need leases of its own. The zombie experiment hangs an incarnation only at hook points; `before_send` is among them, since that is the gap a hang can exploit.
- **The conditional-write rule assumes one writer per campaign.** "The total grew by our amount, so it was ours" is only sound if nothing else allocates to that campaign.
- **Parallel calls go out one after another.** A batch's intents are journaled together and each call is recovered on its own, but the runtime sends the calls in order, which keeps the simulation deterministic. Concurrent sends would leave any subset of the batch in flight at a crash instead of a prefix. Recovery already treats each call on its own, so it wouldn't change.
- **Batching costs escalations.** A crash after a batch's intents leaves all of its calls in doubt, so an unsafe call escalates even if it never went out. `harness_cas` avoids this.
- **The LLM ablations ran one call per reply.** The LLM planners can return several calls (`parallel=True`), but the published LLM numbers predate that and kept only the first.
- **`send` durability leans on SQLite and the disk.** It needs WAL recovery to keep a prefix of the log, and the disk to honor fsync. The tests check which writes fsync; nothing here cuts the power.
- **Positional keys trust the journal.** If the journal is lost or truncated, or a run id is reused for a different goal, step N may be a different call under the same key.
- **Platforms expire idempotency keys** (24 hours is common). A run suspended or escalated for longer would re-send an idempotent call under a key the platform has forgotten. The simulator never expires keys.
- **Escalations are a real cost.** Under this fault mix the plain harness escalates often: every ambiguous allocation, including 500s that never committed in this simulator, so many escalations are false alarms. The benchmark's operator answers as soon as the deadline has passed; a person would take minutes.
- **A crash between an unsafe call's intent and its send still escalates.** It can't be told apart from a crash after the send, and journaling a "sending" marker wouldn't help: the intent already is the last write before the send. The in-process crash points also over-weight this window. It is one point in four, but the real code spends microseconds there. The hard-kill runner kills at uniformly random times and has no such skew.
- **The scripted planner runs at scale; the real LLMs only at small N.** A duplicate in an LLM run can be the model's own repeat decision. The local-model table separates the two run by run where a journal is replayed, by counting steps that took effect twice; for `keys_only` only the comparison with the control row is available.
- **The main benchmark crashes in-process.** The hard-kill runner backs it up with real process kills, but neither one tests power loss or disk failure.

## Why not just Temporal?

In practice, Temporal (or DBOS, or Restate) is the right substrate for this, and it already does the central trick. Workflow code is replayed from event history, and an LLM call made as an activity is recorded, so a replay doesn't re-ask the model. What Temporal deliberately leaves to you is activity idempotency: activities run at least once, and making each external call safe to repeat is the application's job. That is the part this repo works on:

- an **effect class** per tool, with a recovery rule derived from it (re-send, same key, lookup or escalate) rather than one generic retry policy;
- **positional keys** derived from the journal position, the analogue of Temporal's workflow id plus activity id;
- **escalation to a human** as a first-class run state, with an approval gate and budget reservation in front of unsafe calls;
- a **ground-truth benchmark** that counts duplicates on the platform's side, not the agent's.

The runtime here is small so the mechanism stays inspectable and measurable. The effect-class layer would sit on top of Temporal activities, not replace them.

## Roadmap

- Concurrent sends for parallel calls, and the LLM ablations rerun with parallel calls on.
- Key expiry: recover an idempotent step older than the platform's key lifetime by lookup or escalation instead of re-sending.
- Platform-side lookups (allocations by client reference, say) to cut escalations without preconditions.
- A lease-based variant of deadlines for platforms that don't enforce them, with an explicit bound on request lifetime.
- Effect classes as a library over Temporal activities.
- A real-LLM evaluation with a stronger local model at larger N.
