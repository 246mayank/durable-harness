# What durability costs

Generated by `python -m chaos.overhead --runs 300` at commit `d65dab9`. Do not edit by hand. Wall-clock timings: they vary by machine and from run to run.

Machine: Windows 11, AMD64, Python 3.13.5, SQLite 3.49.1; journal files in `C:\` (system temp directory).

300 clean campaign runs per row (8 tool calls each, scripted planner, in-process platform, no faults or crashes), the rows run in a shuffled order each round. Time per tool call covers the whole step: planner, journal writes, fence checks and the in-process HTTP call.

| harness journal | ms per tool call (median) | p95 | added over in-memory | journal writes per tool call | fsyncs per tool call |
|---|---|---|---|---|---|
| in memory (no durability) | 2.88 | 4.76 | 0.00 | 4.5 | 0.0 |
| `normal`: no fsync | 3.19 | 5.21 | 0.32 | 4.5 | 0.0 |
| `send` (default): fsync before each send | 6.75 | 10.49 | 3.87 | 4.5 | 1.0 |
| `full`: fsync every write | 18.49 | 26.21 | 15.61 | 4.5 | 4.5 |

Bare intent appends, 2000 per row, each its own committed transaction:

| journal | ms per append (median) | p99 |
|---|---|---|
| in memory (no durability) | 0.02 | 0.04 |
| `normal`: no fsync | 0.06 | 0.19 |
| `send` (default): fsync before each send | 3.22 | 19.36 |
| `full`: fsync every write | 3.17 | 7.78 |

Fsyncing every write (`full`) costs 4.5 fsyncs and 15.61 ms per tool call here. Fsyncing only before each send (`send`) costs 1.0 and 3.87 ms, with the same guarantee that every call that went out has its intent and deadline on disk. Against a tool that takes 100 ms (a fast remote API), that is 4% on top of each call instead of 16%: a projection from the numbers above, not a measurement. An LLM decision takes far longer than either.
